# CareerOS

> **个人能力画像与动态职业发展路径推荐系统**
>
> 机器学习项目实训 · 第一阶段 MVP

## 一、项目介绍

### 1.1 项目背景

传统职业测评工具通常存在三个问题：

- **重兴趣、轻能力：** 更多关注兴趣和性格，缺乏对实际技能储备的量化分析。
- **缺乏市场数据支撑：** 职业推荐与真实就业市场需求脱节。
- **推荐结果静态固定：** 无法根据个人能力变化和市场需求变化提供持续更新的建议。

CareerOS 希望将个人能力画像、职业技能知识库和就业市场数据结合起来，构建一个面向个人职业发展的智能推荐系统。

### 1.2 核心功能

用户填写个人特征和技能水平后，系统完成以下工作：

| 功能模块 | 功能说明 |
|---|---|
| 个人能力画像 | 记录用户技能、掌握程度及个人特征 |
| 职业方向推荐 | 计算个人能力与职业要求的匹配程度，输出 Top-5 职业 |
| 能力差距分析 | 对比当前能力与目标职业要求，识别能力短板 |
| 职业发展路径 | 根据技能差距生成可交互的职业发展树 |
| 市场需求分析 | 结合招聘数据分析职业及技能的市场需求 |

### 1.3 项目技术路线

项目采用 Flutter + Python 技术体系。

- **Flutter：** 用户交互、能力填报、职业推荐展示和发展树可视化。
- **Python：** 数据处理、职业匹配算法、能力差距分析。
- **FastAPI：** 提供后端接口，连接前端与算法模块。
- **Pandas / NumPy：** 数据清洗与数值计算。
- **Pydantic：** 统一数据模型与接口校验。
- **Pytest：** 自动化测试。

数据来源：

- O*NET：职业信息及职业技能要求。
- 招聘市场数据：根据实际可获取的数据源，采集或整理岗位及技能需求信息。

## 二、开发阶段与目标

项目采用分阶段迭代策略。

### 第一阶段：小组实训 MVP

<badge color="success">当前开发阶段</badge>

**开发周期：约一周**

第一阶段以完成一个完整、可运行、可演示的职业推荐系统为目标。

核心实现：

1. 建立小规模职业—技能知识库。
2. 实现用户技能填报与能力画像。
3. 实现基于技能向量的职业匹配算法。
4. 输出 Top-5 职业推荐结果。
5. 实现三档能力差距分析。
6. 根据技能差距生成基础职业发展路径。
7. 通过 FastAPI 完成前后端数据交互。
8. 使用 Flutter 展示推荐结果和发展树。

**第一阶段算法方案：**

优先采用可解释、易实现的基础算法：

- 技能向量化。
- 余弦相似度计算。
- 加权职业匹配排序。
- 技能等级差值计算。
- 规则化发展路径生成。

第一阶段不强制要求训练复杂深度学习模型。算法必须有明确的计算依据，并能够通过测试数据验证。

市场数据优先使用可获取的真实招聘数据样本，必要时采用固定数据快照完成演示，不将实时爬取作为 MVP 的前置条件。

### 第二阶段：个人毕设迭代

在第一阶段基础上继续扩展，逐步形成完整的个人毕业设计。

计划升级方向：

| 第一阶段 | 后续升级方向 |
|---|---|
| 基础技能画像 | 多维个人能力画像与能力发展轨迹 |
| 余弦相似度匹配 | 预训练嵌入与多特征融合 |
| 固定职业技能权重 | 数据驱动的职业需求权重 |
| 静态招聘数据 | 多来源动态就业市场数据 |
| 三档技能差距 | 更精细的能力差距评估 |
| 规则化发展路径 | 基于技能依赖关系的动态路径规划 |
| 基础推荐排序 | 推荐效果评估、基线对比与消融实验 |
| 基础功能测试 | PSI 技能分布漂移监控与持续更新机制 |

后续升级以实际研究价值和实验结果为依据，不预设必须使用某一种复杂模型。

## 四、项目目录结构

前后端位于同一仓库的两个独立项目目录中：Flutter 只维护客户端代码，FastAPI 及算法、数据处理代码统一归入后端。

```text
CareerOS/
├── frontend/                    # Flutter 项目
│   ├── lib/
│   │   ├── main.dart
│   │   ├── models/
│   │   └── services/
│   ├── pubspec.yaml
│   └── pubspec.lock
├── backend/                     # FastAPI 与算法项目
│   ├── packages/
│   │   ├── core/
│   │   ├── service/routers/
│   │   └── training/
│   ├── configs/
│   ├── data/
│   ├── scripts/
│   ├── tests/
│   ├── .venv/                    # 本地环境，不提交 Git
│   └── requirements.txt
├── docs/
├── .gitignore
└── README.md
```

### 本地启动

后端在 `backend/` 目录运行：

```powershell
cd backend
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
uvicorn packages.service.main:app --reload
```

运行后端测试：

```powershell
cd backend
pytest
```

前端在另一个终端运行：

```powershell
cd frontend
flutter pub get
flutter run
```

### 模块边界

遵循模块解耦原则：

- `core`：定义公共数据结构和业务契约。
- `training`：负责职业匹配、推荐及算法计算。
- `service`：负责 HTTP 接口、业务编排和调用算法。
- `Flutter`：负责用户交互与数据展示，不重复实现核心推荐算法。
- `tests`：验证各模块及完整调用链路。

禁止后端反向依赖训练入口或训练脚本。后续模型升级时，尽量保持后端调用接口不变。

## 八、项目开发规范

### Git 协作

- 各成员只负责自己所属模块的日常开发。
- 公共数据结构修改前必须沟通。
- 不直接向 main 提交未经检查的大量修改。
- 每个功能完成后及时提交。
- 不上传原始大数据、模型缓存及个人环境文件。

推荐提交格式：

```text
feat: add career recommendation
fix: correct skill gap calculation
docs: update project specification
test: add API integration tests
refactor: improve data processing
```

### 数据与接口规范

统一使用 Pydantic 定义核心数据结构。

API 响应统一采用：

```json
{
  "code": 200,
  "message": "success",
  "data": {},
  "requestId": "xxx"
}
```

前端需要同时检查 HTTP 状态码与业务 code。

所有模块必须遵循统一的数据字段和业务口径，不允许各自定义互不兼容的数据格式。

## 九、项目最终目标

CareerOS 不只是一个根据用户兴趣推荐职业的测评工具，而是希望建立个人能力与真实就业需求之间的联系。

我们希望最终实现：

**了解自己具备什么能力 → 找到适合自己的职业方向 → 发现与目标职业之间的差距 → 明确下一步能力提升方向。**

第一阶段完成可运行的职业推荐 MVP；后续以个人毕业设计为基础，继续研究动态职业需求建模、个性化推荐和职业发展路径规划。

让职业推荐从一次性的结果展示，逐步发展为能够持续更新的个人职业发展辅助

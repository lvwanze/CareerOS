# 招聘岗位样本数据源调研报告（M2 市场分析）

- 调研人：代旭（后端 / 市场分析数据）
- 日期：2026-11-20（v2，补齐拉勾源）
- 依据：`problem.md` §4.3 / §6、`data_contract.md` §5 / §6、讲师红线 23（数据量 ≥2 万条、维度 ≥2 个）、红线 3（明细数据不进 Git）
- 目标：为"职业市场分析"模块确定可获取、可复现、可合规使用的招聘岗位样本，并给出字段方案

## 一、结论

**采用「拉勾技术岗 + 校招宝 recruit-hub」双源合并，已清洗落表 35,043 条。**

四个判断：

1. **规模达标。** 合并去重后 35,043 条（大陆 32,331），是红线 23 要求（≥2 万条）的 1.75 倍。维度 7 个：城市 / 学历 / 工作经验 / 薪资 / 岗位大类 / 平台 / 发布时间。
2. **拉勾是主力源。** 14,736 条技术岗，薪资、学历、经验、JD 正文**全部 100% 有值**，正好对应 CareerOS 的 IT 职业范围（后端 7,517 / 运维 4,071 / 测试 3,211 / 前端 2,625 / 人工智能 2,581 / 移动 1,315）。
3. **技能维度从"做不了"变成"可做"。** 拉勾每条都有 JD 正文（平均 367 字），是抽技能需求的原料；此前判断"无技能字段"只针对 recruit-hub 一个源。
4. **有一个必须写明的折扣：拉勾数据是 2022-08 ~ 2024-01 的，不是当前市场。** 做"技能需求结构"和"职业间差异"没问题，做"2026 年最新行情"不能用它。当前行情那部分由 recruit-hub（2026-08 ~ 2026-10）承担。

## 二、需求口径

`problem.md` §4.3 明确市场分析要出五类结果：

| 需求 | 能否支撑 | 字段 / 做法 |
|---|---|---|
| 岗位需求数量 | ✅ | 一行一岗，按 `job_category` / `city` / `platform` 计数 |
| 核心技能需求 | ✅ 可做 | 拉勾 `job_descriptions.csv` 的 JD 正文，关键词 + 词典抽取 |
| 薪酬分布 | ✅ | `salary_min` / `salary_max`，合并后 52.7% 可解析（拉勾源 100%） |
| 学历和工作经验要求 | ✅ | `education` 70.0%；`work_year` 42.1%（仅拉勾源有） |
| 不同时间段的技能需求变化 | ✅ 可做 | 拉勾有 `publish_date`，可做月度分布；跨源趋势需按 `platform` 分组 |

## 五、字段方案（建议稿，待契约确认）

`data_contract.md` §6 只列了 `JobPosting` 这个名字，**没有定义任何字段**。下表是建议稿，**未经 ADR-006 变更流程确认前不得冻结**，当前 `status=draft`。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| job_id | str | 是 | `JP-LG-` / `JP-RH-` + 去重键 sha1 前 10 位，重跑不变 |
| platform | str | 是 | `lagou` / `recruit_hub`，统计时据此分组 |
| source_ref | str | 是 | 原始标识：拉勾为 positionId，recruit-hub 为岗位链接 |
| position_name | str | 是 | 岗位名称（原始文本） |
| job_category | str | 是 | 统一大类：技术/数据/产品/设计/管培生/职能/市场运营/其他 |
| job_subcategory | str | 否 | 原始细分：拉勾 bigcategory（后端开发/运维/测试/前端开发/人工智能/移动开发） |
| company_name | str | 是 | 公司名称 |
| company_size | str | 否 | 公司规模，仅拉勾源有 |
| industry | str | 否 | 行业 |
| city | str | 否 | 标准化城市 |
| region | str | 是 | `mainland` / `overseas` |
| education | str | 否 | 博士/硕士/本科/大专/不限 |
| work_year | str | 否 | 原始经验档位，仅拉勾源有 |
| salary_min | int | 否 | 月薪下限（元） |
| salary_max | int | 否 | 月薪上限（元） |
| batch | str | 否 | 校招/实习/社招/全职 |
| publish_date | date | 是 | 发布日期，ISO 8601 |
| has_jd | str | 是 | `1`/`0`，是否在 `job_descriptions.csv` 有正文 |

**另设一张表**：`job_descriptions.csv`（`job_id` / `position_detail`），只存拉勾 14,736 条 JD 正文。理由：正文平均 367 字，塞进主表会让主表膨胀到 8 MB 且每次统计都要跳过它；拆开后主表干净，技能抽取时按 `job_id` join。

**要提的契约变更**：新增 `JobPosting` 模型（18 字段）+ `JobDescription` 模型（2 字段）。`JobSkill` 关系表等技能抽取跑通后再提。

## 六、技能维度怎么做

拉勾 JD 正文是原料，但**还不能直接算"技能需求热度"**，中间有两步：

1. **抽词**：从 `position_detail` 里抽技术名词。可直接用词典匹配（Java / Python / MySQL / Redis / Spring / React / Flink…），比通用 NLP 稳，也不依赖外网模型。
2. **对齐 skill_id**：CareerOS 现有 `skills.csv` 只有 35 个 O*NET 技能，其中只有 `Programming` 一个技术技能，Java/React/SQL 都落不到现有 `skill_id`。要么扩 O*NET Technology Skills（31,821 行软件技能），要么技能需求分析独立成一张 `skill_demand` 表，先不挂 `skill_id`。

**建议**：第一阶段做第 1 步（抽词 + 词频 + 城市/岗位交叉），产出"哪些技术词在哪些岗位、哪些城市出现最多"，挂 `skill_id` 留给第二阶段。这样不动已冻结的 v0.5.0 职业技能表，也不阻塞市场分析出图。

## 八、已知缺口

### 缺口 1：两源时间不重叠

拉勾 2022-08 ~ 2024-01，recruit-hub 2026-08 ~ 2026-10，中间隔了两年半。**跨源做"时间趋势"是错的**，会把断档当趋势。正确做法：趋势只用单源做，跨源只做"结构对比"并在图上标清两条时间轴。

### 缺口 2：技能未挂 skill_id

见第六节，第一阶段只出词频，不挂 O*NET 技能 ID。

### 缺口 3：recruit-hub 的「其他」占 6,686 条

岗位名极度分散（"技术员" 78 次、"信息技术岗" 30 次、"综合管理岗" 23 次，长尾每个个位数），关键词规则覆盖不到。若要做细，需人工标注一批种子样本训练分类器（第二阶段）。**拉勾源不受影响**，它的 `bigcategory` 是平台自带分类。

### 缺口 4：拉勾无城市以外地域信息

只有 `city` / `district`，没有经纬度或区域编码。要画地图需另做城市名到行政编码的映射表。

### 缺口 5：JD 正文被截断在 400 字符（影响最大）

实测长度分布：**9,038 条正好 400 字符（61.3%）**，最长也是 400，中位数 400。这是原始抓取时的字段长度限制，不是自然结束——抽查结尾都是「…并了解其架构和实现原理； <br」这种半截。

**影响**：每条 JD 只保留前 400 字，通常覆盖"岗位职责"+ 部分"任职要求"，后半段技术栈会被切掉。后果有两层：

1. 技能词频会**系统性低估**，且低估程度与 JD 前段啰嗦程度相关（写岗位职责越长，被截掉的技能越多），偏差不均匀。
2. 因此技能统计只能做**相对比较**（哪个方向更需要 Java），不能做**绝对占比**（多少比例的岗位要求 Java）。

出图时标题必须写"基于 JD 前 400 字"，不能写"基于完整 JD"。

### 缺口 6：职业覆盖只有 6 个方向，且偏社招

拉勾去重后覆盖：后端 5,691 / 运维 3,091 / 前端 1,950 / 测试 1,627 / 人工智能 1,447 / 移动 930。

对照 CareerOS 的 28 个职业，**没有样本**的有：5 个金融分析类（13- 开头全部）、信息安全分析师、数据库管理员/架构师、计算机系统分析师、精算师、运筹分析师、统计学家、商业智能分析师、生物信息学家、区块链工程师、网页设计师、用户支持专家。

另外经验分布偏社招：3-5 年 5,738、1-3 年 3,499、5-10 年 2,620、**在校/应届仅 738（5.0%）**。CareerOS 面向学生群体，这里存在人群错位——技术栈参考价值仍在，但"应届门槛"类结论不能用这份数据下。

### 缺口 7：小样本格子

城市 × 方向交叉后，部分组合不足 100 条：杭州 × 人工智能 96、成都 × 测试 90、广州 × 移动 86、成都 × 移动 78、广州 × 人工智能 72、杭州 × 移动 61、成都 × 人工智能 43。这些格子不能单独出结论，只能合并或标注样本量。

## 九、复现方式

```bash
# 生成（数据负责人运行；下游只读成品 CSV）
python scripts/clean_recruitment.py
```

输出：

```
backend/data/processed/job_postings.csv            35,043 行 × 18 列
backend/data/processed/job_descriptions.csv        14,736 行 × 2 列
backend/data/processed/job_postings.manifest.json
```

脚本用纯标准库（csv / json / hashlib / re / pathlib），与 `build_dataset.py` 同一套写法：规则参数化在文件顶部、每步 `log_step` 留痕、关键处 `assert` 对账。不引入第三方依赖——本机 `python` 解释器装不上 pandas，用标准库是唯一在组内各处都能跑的选择。

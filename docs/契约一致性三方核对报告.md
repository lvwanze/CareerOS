### 2.2 不一致明细与建议改法

**A. `user_id` 必填规则（后端代码 pending）**

- data_contract §3.1 原文：`| user_id | str | 是 | 用户唯一标识 |`（必填）
- 代码 d0ea59a：`ProfileInput.user_id: Optional[str] = Field(None, ...)`（缺失可接受，返回时填 anonymous）
- 后端口径（11-20 已定）：必填，`str`、`strip()` 后长度 1～64，缺失/空白 → 422，loc=`profile.user_id`；但代码未落地，明确要求测试侧暂按兜底跑。
- **建议**：后端落地校验后，把契约 §3.1 与代码同步为「必填、1–64」，测试侧再把 TC-EX-09 从兜底改为严格断言 422 + 校验 loc。**归属：代旭**。

**B. `goal_description` 上限（后端代码 pending）**

- data_contract §3.1 原文：`| goal_description | str | 个人目标描述 |`（career_goals 子表，无上限）
- 代码 d0ea59a：`ProfileInput` 只显式定义 `user_id`、`skills`，其余字段 `extra="allow"` 原样接收，`goal_description` 无任何长度校验。
- 后端口径（11-20 已定）：选填，上限 2000 字符，按 Python `len()` 码点计，超限 422，loc=`profile.career_goals.goal_description`；代码未落地。
- **建议**：后端落地后，在契约 §3.1 补「选填、≤2000 字符」说明，测试侧把 TC-EX-05 从健壮性检查升级为 2001 字严格 422 断言。**归属：代旭**。

**C. 发展树节点 `status` 枚举（2026-11-25 已收口为 3 档）**

- data_contract §3.7 DevelopmentNode 原文 5 档：`not_started` / `learning` / `needs_improvement` / `needs_verification` / `completed`
- 代码 d0ea59a 两套发展树模型均为 3 档：`DevelopmentNode.status` 与 `TreeNode.status` 都是 `Literal["not_started", "in_progress", "mastered"]`
- 注意：`learning` vs `in_progress`、`needs_improvement`/`needs_verification`/`completed` vs `mastered`，**名称和数量都对不上**。
- 另有算法侧 SkillGap.status 3 档（`mastered`/`needs_improvement`/`needs_verification`，与契约 §3.6 一致）和前端界面两态。
- **处置（2026-11-25）**：代旭 PR#18 以"代码与 Flutter 均只实现 3 档、收到 `learning` 会整页崩"为依据，把 `data_contract.md §3.7` 收敛为 3 档，并新增 §3.8 CareerTree；测试侧跟随收口——`reference/schemas.py` 的 `NodeStatus`、`test_contract.py::TC-DATA-12`、TC-API-05/06 全部改按 3 档断言，旧值 `learning`/`completed` 作为非法值回归防护。原 Q6 关闭。
- **复测（2026-11-26）**：PR#18 已合入 main（`a36acd6`），TC-DATA-12 在真实后端单跑 PASSED（3 档通过、旧值 `learning`/`completed`/`needs_verification` 与 `unknown` 均返 ValidationError），契约/代码/测试三方口径实测一致。
- 注意：`needs_improvement`/`needs_verification` 仍是算法侧 `SkillGap.status`（能力状态）的合法值，与发展树任务状态是**两个字段**，不要一并删除。

**D. `requestId` 残留（仅展示文档）**

- 契约与 api_spec 均为 `request_id`，代码也是 `request_id`，三方已一致。
- 仅总体 README（第 440 行附近）残留驼峰 `requestId`，属展示文档笔误，不影响代码与契约一致性。
- **建议**：README 负责人改为 `request_id`；测试侧 TC-DATA-15 已锁死 `request_id`，出现驼峰即判违规。**归属：吕宛泽**。

## 三、给第③项补齐后的判定口径

- 三方核对完成，定位 4 处差异（A/B/C/D），其中 A/B 是后端已定规则、代码 pending，C 是公共结构待拍板，D 是展示文档笔误。
- 差异中**没有一处是测试侧漏测或写错断言**——测试用例已按契约/已确认口径断言，pending 项按兜底处理并在核对表留痕。
- 第③项由「×」补齐为「**已逐字段核对、差异定位清楚、归属明确、待对应负责人落地**」，可以据此答辩与推进，不应表述为「三方已完全一致」。

## 四、答辩口述版（老师问到"文档和代码一致吗"直接说）

> 我做了一次三方核对，把接口规范、数据契约和后端代码逐字段对齐。大部分字段是一致的——像请求追踪号、统一错误信封、技能等级整数校验、匹配分范围，尤其后端合入那次改动之后都对齐了。
>
> 还有四处差异我定位得很清楚：一是用户 ID 必填规则，契约写必填、代码目前还是选填；二是目标描述的长度上限，规则定了 2000 字符但代码没落；三是发展树节点状态，契约五档、代码三档、前端还显示两态，这个要前后端拍板统一；四是一个 README 里的驼峰字段名笔误，代码和契约本身是对的。
>
> 这三处规则类的差异都是后端已经定了口径、代码还没落地，或者要前后端共同拍板的公共结构，不是我这边漏测。我的用例是按契约和已确认口径写的，没落地的部分用兜底断言并留了痕，等代码落地、commit 到位，我就把断言收紧成严格校验。

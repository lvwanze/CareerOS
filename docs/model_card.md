## 一、模型用途

本模型回答一个问题：**给定用户已填的技能与自评等级，哪几个职业最贴近他现在的水平，以及每个职业还差哪些技能。**

输出用于驱动 App 的「职业推荐卡片」与「能力差距清单」两屏。完整链路为：

`用户画像 → 技能画像 → 职业匹配 → Top-5 推荐 → 能力差距 → 发展路径 → Flutter 展示`

本模型覆盖其中「职业匹配 → 能力差距」一环，不负责发展路径生成（M4）、不负责用户画像采集（前端）。

### 本模型不做什么

| 不做 | 原因 |
| --- | --- |
| 不预测就业概率、录取概率、薪资 | `match_score` 是内部相对指标，无任何外部标签校准 |
| 不评估用户真实能力 | 输入是**用户自评**，模型只做一致性核对，无法验证真伪 |
| 不做职业推荐之外的建议 | 不做简历诊断、不做学习计划排期 |
| 不引入语义模型 / 向量检索 | MVP 阶段技能维度仅 35 个，加权求和已足够且完全可解释 |

## 二、输入

`recommend(profile, top_k=5, diversity_theta=0.90)`，`profile` 结构对应契约 §2.2：

| 字段 | 类型 | 必填 | 取值范围 | 缺失时行为 |
| --- | --- | --- | --- | --- |
| `user_id` | str | 否 | — | 仅透传，算法不使用 |
| `skills[].skill_id` | str | 是 | 35 个已知技能 ID | 不在白名单则**告警并忽略该条** |
| `skills[].self_level` | int | 是 | 0 ~ 4 | 缺省按 0；越界直接 `ValueError` |
| `skills[].evidence_level` | str | 否 | `none / self / course / project / work / certificate / test` | 缺省 `none`；未知值告警后按 `none` |

**两条输入约定：**

1. **没填 = 0 级 + 无证据。** 用户画像里不出现的技能不会报错，按 `(0, "none")` 参与计算。这是「分母用职业全量技能」得以成立的前提。
2. **`self_level` 越界不宽容。** `[-1]` 或 `[5]` 直接抛 `ValueError`，不做截断——静默截断会让用户以为 5 级被记录了。HTTP 边界由 service 层 Pydantic 拦成 422，不会漏成 500。

## 三、输出

返回 `list[dict]`，每项对应契约 §3.5，另附 §3.6 的差距明细：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `occupation_id` | str | 职业 ID |
| `occupation_name` | str | 职业英文原名（中文名由后端映射层补充，算法不使用） |
| `match_score` | float | 匹配分，`[0, 1]`，保留 3 位小数 |
| `matched_skills` | list[str] | 已达标技能 ID |
| `skills_to_improve` | list[str] | 待提升技能 ID |
| `skills_to_verify` | list[str] | 待验证技能 ID |
| `recommendation_reasons` | list[str] | 推荐依据，最多 4 条 |
| `skill_gaps` | list[SkillGap] | 该职业全部要求技能的逐项差距（`gap` 为 int） |

**条数约定（重要）**：返回长度在 `[0, top_k]` 之间，**不保证等于 `top_k`**。去重会剔除相似职业，`top_k` 也不保证小于可选上限。前端必须按「最多 `top_k` 张卡片」渲染，不能写死 5。

**排序约定**：`match_score` 降序；分数相同按 `occupation_id` 升序。排序使用全精度分数，`round(3)` 在排序之后执行——若先四舍五入再排序，并列项顺序会随字典遍历顺序漂移。

## 四、算法

四步：算权重 → 逐职业打分 → 三档判定 → 排序去重。全部为确定性计算，无随机数、无训练过程。

### 4.1 技能权重

```
w = ((IM - 1) / 4) × IDF
IDF = ln((1 + N) / (1 + df)) + 1        N = 28（职业总数），df = 出现该技能的职业数
```

- `IM` 为 O*NET 原始重要度（1~5），`(IM-1)/4` 压缩到 `[0, 1]`。数据实际值域 3.00~4.88，故归一化后落在 `[0.50, 0.97]`。
- IDF 取**平滑写法** `ln((1+N)/(1+df)) + 1` 而非 `ln(N/(1+df))`。后者在技能覆盖全部职业时给出约 `-0.035` 的负值，意味着「掌握通用技能反而扣分」，逻辑上不成立；平滑后最通用的技能 IDF 恰为 `1.0`，即不加权也不惩罚。
- 实测：IDF `1.0000 ~ 3.6741`，权重 `w` `0.5000 ~ 2.0684`（均值 0.7800）。

### 4.2 匹配分

```
match_score = Σ(wᵢ × 达成度ᵢ) / Σwᵢ
达成度 = min(self_level / required_level, 1.0)
```

**分母是「该职业挂载的全部技能权重和」**，不是「用户填了的技能权重和」。实测每职业 `Σw` 在 `7.4768 ~ 22.9604`。

这一条是整个模型最关键的取值口径：

| 分母口径 | 后果 |
| --- | --- |
| 职业全量技能（现行） | 没填的技能按 0 级计入，分数反映「覆盖了多少要求」 |
| 只算用户填了的技能 | 用户填的都是自己会的，分子 = 分母，**人人 1.0 分**，推荐完全失效 |

达成度在超过要求时封顶 1.0，多出来的能力不给额外加分，避免「刷级刷高匹配度」。

举例（真实数据，`Software Developers`，16 项技能，`Σw = 11.5018`）：用户填 2 项均为 4 级，得分 **0.0963**。分数低不代表推荐错误，而是说明该职业的大部分要求还没覆盖——这是「诚实」的代价，也是它可解释的来源。

### 4.3 三档判定（顺序不可交换）

```
① self_level <= 0                  → needs_improvement  待提升
② evidence_level == "none"         → needs_verification 待验证
③ self_level >= required_level     → mastered           已具备
④ 其余                              → needs_improvement  待提升
```

**第 1 条必须放最前。** 「没填」在算法眼里是「0 级 + 无证据」，若先判第 2 条，空画像用户会得到「你需要验证这些技能」——他从没说过自己会，无从验证。没填 ≠ 待验证，没填 = 不会。

**第 2 条必须在第 3 条之前。** 否则「自评 4 级但拿不出证据」直接落 `mastered`，`needs_verification` 这一档几乎永远不触发，契约要求的第三档形同不存在。

### 4.4 相似职业去重

```
Jaccard(A, B) = |A ∩ B| / |A ∪ B|         A、B 为职业技能集合
```

按分数从高到低遍历，与**已入选**的职业逐一比较，`Jaccard > diversity_theta` 则跳过。

实测本数据集 378 个职业对，相似度均值 **0.6655**、中位 0.6667，超过 0.90 的有 3 对：

| 职业对 | Jaccard |
| --- | --- |
| Software Developers ↔ Blockchain Engineers | **0.9412** |
| Statisticians ↔ Bioinformatics Technicians | 0.9375 |
| Software Developers ↔ Web Developers | 0.9375 |

不去重时 Top-5 会同时出现「区块链工程师」和「软件开发人员」，用户拿到的是 1 个方向重复 2 次。去重后两者只保留分数高的一个。

**阈值影响**（实测，本数据集）：

| `diversity_theta` | 可选职业数 |
| --- | --- |
| 1.01（关闭） | 28 |
| 0.95 | 28 |
| 0.90（默认） | 26 |
| 0.85 | 22 |

### 4.5 推荐依据生成

最多 4 条：先取权重最高的 2 项已达标技能（`"阅读理解 已达标"`），再补差距 ≥ 2 级的待提升技能（`"数学 还差 3 级"`）。用真实技能名拼装，不使用固定文案。

### 6.2 后端集成测试（`backend/tests/test_recommend.py`）

`pytest` **7 passed**，覆盖接口字段名、`skill_gaps` 按 `importance` 降序、去重生效、`top_k` 上限、中文名映射。

### 6.3 分数区间（当前数据集实测）

| 画像 | Top-5 `match_score` |
| --- | --- |
| 高匹配（12 项技能，2~4 级，含编程与数学 4 级） | 0.751 / 0.714 / 0.705 / 0.647 / 0.631 |
| 低匹配（5 项通用技能，均 2 级） | 0.383 / 0.334 / 0.312 / 0.307 / 0.297 |
| 空画像 | 返回 5 条，最高分 0.000 |

分数绝对值偏低是分母口径的必然结果，不是缺陷。可比较的是同一份输入内的**相对排序**。

### 6.4 明确未验证的部分

| 未验证 | 说明 |
| --- | --- |
| 准确率 / 召回率 / NDCG | **无标注数据**：没有任何「这个用户真实适合哪个职业」的 ground truth，无法计算排序质量指标 |
| 用户满意度 | 未上线，未做用户调研 |
| 跨数据集泛化 | 仅 28 个职业、35 个技能，超出该范围的职业不做推荐 |
| 中文名影响 | 已验证无影响：中文名置空或替换为乱码，28 个职业排序与分数完全一致（6 位小数） |

**结论：当前验证的是「确定性 + 契约一致性 + 边界行为」，不是「推荐得准不准」。** 任何对外表述都不应把 0.751 说成「匹配度 75%」或「录取概率 75%」。

## 七、已知局限

1. **无准确率指标。** 缺少标注数据，无法给出排序质量评估。目前的分数只是模型内部相对值，跨用户的分数不可比较。D4 阶段可做的替代方案：构造 30~50 个人工标注画像做一致性检查（Top-1 是否落在人工认可的前 3 个之内），但仍不等于线上准确率。
2. **输入依赖自评，无法校验真伪。** 模型只能通过 `evidence_level` 区分「有证据」与「只有自评」，无法判断用户是否高估自己。全填 4 级的用户会拿到接近满分的推荐，这是设计上接受的偏差。
3. **技能粒度偏粗。** 35 个技能多为通用认知技能，缺专业技术技能，导致职业区分度低（378 对平均 Jaccard 0.6655）。当前靠 IDF 加权与去重缓解，根因需从 O*NET Technology Skills 扩充技能表解决。
4. **`required_level` 实际值域仅 1~3。** 契约定义 0~4，但 `IM >= 3.0` 筛选后本数据不出现 0 与 4 级。`gap` 理论上限为 3，不会出现 4；测试不宜按 0~4 全档位断言。
5. **`evidence_level` 枚举未在契约中冻结。** 契约 §2.2 标注为「待确认」，模型已按 7 个值实现（`none/self/course/project/work/certificate/test`）。需在契约下一版固化，否则前后端各写一套会静默失配。
6. **算法层的宽容策略不适用于 HTTP 边界。** matcher 遇到未知 `evidence_level` 只告警并按 `none` 处理，因为它可能被脚本、离线任务直接调用，不应因一个字段中断整批计算；HTTP 入口由 Pydantic `Literal` 拦成 422。两层分工明确，但若有人绕过 service 层直接调 matcher，脏数据不会报错。
7. **中文名不在模型内。** 中英文映射由后端 `backend/data/reference/*_name_zh.csv` 提供，算法全程只用 ID 与数值字段。好处是映射可独立维护，代价是缺映射时前端会显示英文原名。

## 九、复现方式

**跑算法本体**（只读 `backend/data/processed/`）：

```bash
python backend/tests/smoke_test.py
```

输出 10 项检查结果、Top-5 分数区间与 `MODEL_VERSION`。任一画像分数与本文档记录不一致，即说明算法被改动。

**跑接口链路**：

```bash
cd backend && python -m pytest tests/ -q
```

**回归基线**：`backend/tests/profiles/d4_cases.json` 固定了输入画像与期望分数（容差 0.01），可脱离测试框架直接 POST 到 `/api/v1/recommendations` 复现。

**修改参数的后果自查**（改前先看这张表）：

| 改动 | 后果 |
| --- | --- |
| `diversity_theta` 调高到 1.0+ | 关闭去重，相似职业会同时出现，可选数回到 28 |
| `diversity_theta` 调低到 0.85 | 可选数降到 22，可能过度剔除正常差异的职业 |
| 分母改为「用户已填技能」 | 所有人接近 1.0 分，推荐彻底失效 |
| 交换三档判定的 1、2 条 | 空画像用户全部变成「待验证」 |
| 先去重后排序 | 保留的可能不是高分职业 |

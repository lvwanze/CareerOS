# 架构测试交付说明（M5 / 新清单 P1）

基准：`origin/main` `453841f`；对应清单：《CareerOS 答辩验收清单》6.3 M5 P1
「增加架构测试」，依据方案 A1「架构测试」。

## 一、做了什么

在 `backend/tests/architecture/` 新增 4 条架构测试，用 AST 静态扫描生产代码
（`backend/packages/`），检查四类约束；并把架构检查作为**独立一步接入唯一质量门**
`scripts/ci.py`（第 3/5 步），先于 pytest 拦截架构违规。本地与 GitHub Actions
调用同一脚本，线上线下同一套。

| 测试 | 约束 | 现状判定 |
|---|---|---|
| `test_service_not_import_training` | service 不依赖 training | recommend→inference 按 ADR-009 放行（推理入口，非训练入口）；新增依赖即失败 |
| `test_production_no_syspath_or_chdir` | 生产代码不改 sys.path / 不调 os.chdir | 生产代码 0 处越界；新增即失败 |
| `test_data_dir_not_scattered` | 数据目录推算不散落 | 现状 4 处（3 router + matcher）登记基线；新增第 5 处即失败 |
| `test_data_fingerprint_intact` | 数据指纹 | manifest frozen + 三表 sha256 与 git blob 规范字节一致 |

**为什么没有 `.importlinter` / `.pre-commit-config.yaml`**：本仓库的架构约束用自研
AST 扫描（`backend/tests/architecture/test_architecture.py`）实现，已覆盖分层依赖、
`sys.path`/`os.chdir`、数据目录推算与数据指纹四类，并接入质量门第 3 步自动执行。
引入 import-linter 需新增第三方依赖与单独配置，与现有 AST 扫描能力重复；
因此**以自研 AST 扫描替代 import-linter，理由：不新增依赖、规则与测试同库可追溯**。
不是遗漏，是有意取舍。

## 二、为什么用「基线 + 显式放行清单」

组长点名的三处"越界"都是真实存在、且有决策依据的现状：

1. `conftest.py` 用 sys.path —— 测试引导代码，为让一键包在扁平/分类两种目录
   结构下都能 `from factories import ...`，属测试侧机制，**不在生产代码
   `packages/` 扫描范围内**（架构测试约束的是生产分层，不是测试脚手架）。
2. `recommend.py:18` 导入 `training.inference` —— **推理**入口 `generate_recommendations`，
   不是 ADR-009 禁止的"训练脚本/训练入口"；README:335 亦写明"service 调用算法"
   属业务允许。新清单 5.2 指出它与方案 A1「api 只依赖 core」有口径冲突，须由
   M3 代旭补专门 ADR 或收敛数据入口后再收紧，故登记放行。
3. 三个 router 各算一次 `parents[3]`、matcher 算 `parents[2]` —— 缺统一 data
   入口层（归 M2/M3），单次提交内 M5 不越界重构他人代码，登记为基线。

若写死"零容忍"，架构测试一上 CI 立刻全红，反而违背"架构测试进入 CI"的验收。
因此采用放行清单：每条含**位置、理由、依据/归属**，扫出的越界在清单内则放行、
不在则失败。这样做到三点：架构测试真的进 CI、违规真的挡得住、M5 不碰生产代码。

放行清单在 `backend/tests/architecture/baseline.py`，删除/整改越界后应同步删除
对应条目——测试会在放行项已消失时主动 `pytest.fail` 提示清理，防止基线永久化。

```bash
  PASS  coverage (exit=0)       # 91%（733 stmts，观测值，无硬阈值）
质量门全绿 ✅
```

**违规拦截验证**：临时在 `service/routers/health.py` 注入一条
`from packages.training import matcher`，架构测试立即失败并精确报出
`packages.service.routers.health -> packages.training`；还原后 `git diff` 为空，
生产代码零残留。

## 四、答辩可讲的三句话

1. "架构测试用 AST 扫生产代码，查分层依赖、路径 hack、数据目录散落和数据指纹，
   作为独立一步进了 CI，违规会直接让构建失败。"
2. "我没有把现状一刀切判红——service 调推理、conftest 用 sys.path、数据目录推算
   这三处都有既有依据，我用显式放行清单登记，每条写清位置和理由，归属到人；
   新增越界才失败。这样既守住了架构，又没越界改别人的代码。"
3. "放行清单带自清理：越界真被修掉后测试会提示删条目，不会让基线 permanent 化。"

## 五、边界

- 未改任何生产代码（`backend/packages/` 与 `service/training` 归属 M3/M2）。
- 未改他人测试；架构测试是本模块新增独立目录。
- `.mailmap`（P1 另一项）不在本次范围——它依赖五位负责人身份对应，需组长确认后做。

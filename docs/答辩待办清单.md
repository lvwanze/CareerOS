# 1　文档说明与基准

本清单用于 CareerOS 答辩前的自检与分工核对、。对照材料有两份：一是老师下发的《diabetes-risk 项目架构设计方案》两张图，即 18 行能力矩阵（每格标注「直接复用 / 改一改 / 重写」）与五站流水线架构图（数据 → 训练 → 上线 → 服务 → 页面，横切监控、地基与质量两条带，图上另标 5 个契约）；二是仓库现状，基准为 origin/main 的 d0ea59a（2026-11-25 09:34）。

第一至第五章回答仓库长什么样、为什么这样设计、包之间怎么依赖，属于说明性内容；第六章起是待办本体，原有条目全部保留并按能力矩阵补齐缺口；第七章单列老师点名的加分项。

11-25 对 d0ea59a 逐条复核后，以下 5 条更正覆盖本清单早期版本的说法。早期版本以 d925839 为基准，且部分前端事实取自工作区里一份未提交的接通版本；该改动现已确认存放在 stash@{0}，不是 main。

## 4.1　模块职责与取舍

表7　核心模块职责与取舍

| 模块 | 职责 | 为什么这样设计 | 代价与风险 |
| --- | --- | --- | --- |
| core/schemas.py（153 行） | 唯一的契约定义处：统一响应信封 ApiResponse（code / message / data / request_id），request_id 用 default_factory 生成 req_ 加 8 位十六进制（:11-14）；SkillGap.status 三档（:24），DevelopmentNode、TreeNode 状态三档（:66、:140） | 前端只认一种响应形状，异常与正常走同一条解析路径；枚举收在 core，让「词表只有一处」在代码层可检查 | request_id 在响应模型实例化时各自生成，一次请求多个 id，既不写日志也不回响应头；状态词表实际有三套（两个节点模型分别用 name 与 skill_name），收在 core 但没收敛成一份 |
| core/name_text.py（33 行） | 中文名 BOM 与 nan 脏值清洗，被 occupations.py:26 与 recommend.py:7 使用 | 数据侧脏值不该在展示层各修一遍；单独成模块便于测试锁定清洗规则 | 规则固定、覆盖面窄，新增脏值类型需同步改代码与测试 |

## 4.3　关于「两条索引路径」的准确说法

早期清单写成「训练与服务没有共用索引构建路径」，实测更精确：构建函数是共用的。inference.py:110 调 build_index，而 matcher.py:435 就是 build_index = _build_index 的公开别名（__all__ 见 :441）。真正没共用的是两件事。

一、读表与列名映射

在线由 service 用 csv.DictReader 组装后传进 _build_index；离线由 matcher._load_data()（:122）用 pd.read_csv 自己读三表再调同一个 _build_index。两条路径的输入形状靠人肉保持一致，没有测试锁定。

二、缓存

_CACHE（:70、:137-170）只挂在 _load_data() 上，而生产链路根本不经过它——全仓调用 _load_data() 的只有 tests/smoke_test.py:86-87，那两行正是在断言第二次调用命中缓存。所以「连续两次请求第二次不重读 CSV」这条验收在当前代码下必然失败，失败原因不是缓存坏了，而是缓存不在生产路径上。

据此，M2 第二条 P0 的任务应改为：收敛出单一 index 入口（读表、列名映射、权重预计算、缓存），让在线与离线都走它，验收看第二次请求不再解析 CSV。

☐ 加分项一：把解释做成可加性贡献（M2 主，M4 配合）

为什么老师会追问：match_score 是黑箱里的一个数，「为什么是 0.207」问一句就露底。定性理由（现在的 _build_reasons）回答不了「各项加起来是不是就是总分」。

现状：matcher.py:241 的实现是 match_score = Σ(w × 达标度)/Σw，本来就是加权和。矩阵把这格标成「重写」，是因为糖尿病风险项目用的是 logit/SHAP 分解，照搬不过来；但对我们反而更简单——逐项贡献 c_i = w_i × 达标度_i / Σw 求和严格等于总分，不需要采样近似，这是全场最容易做实的一条加分项。

最小实现：_score_occupation 顺带返回每项贡献；SkillGap 增加 contribution（或新增 score_contributions 数组）；契约与 api_spec.md 第 4 节同步；前端在推荐卡片把「匹配依据」升级为逐项贡献条（recommendation_page.dart:228 附近），并显示「各项之和 = 总分」的自检行。

验收：任选一条推荐，界面或响应里能取到每项技能的贡献值，且 sum(contributions) 与 match_score 在 1e-9 内相等（写成测试，不只口头声明）；改一个 self_level 后贡献分布随之变化且仍闭合。

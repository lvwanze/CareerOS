### 2.2 测试规模口径说明

清单/历史记录里的 `def test_` 函数数、89/90、135、144/147 是同一批测试的几种计数口径，不是数字冲突。
以 2026-11-27 合并态（`96db006` + M2 枚举冻结 `4b8b555` + 本 PR 防漂移测试）实测为准：

| 口径 | 数字 | 含义 |
|---|---|---|
| `def test_` 函数数 | 122（全仓）/ 65（acceptance） | 源码里定义的测试函数个数，`@parametrize` 算 1 个 |
| pytest 收集数 | 90（acceptance） | 验收套件参数化展开后的可执行用例数，即通常所说的「90 条」 |
| pytest 收集数 | **147（backend/tests 全量）** | 验收 90 + 后端原有测试 + 架构 4，展开总数；头条口径 |
| 历史 passed 数 | 89 / 131 / 135 / 144 | 旧基准（PR#18~#21）的全量通过数，已被 147 取代，不再引用 |

**换算关系**：122 个函数 → 参数化展开为 147 条；其中 acceptance 65 个函数 → 90 条。
增量来源：`96db006` 基准 144 条 → 赵的 TC-EX-10（枚举越界，+1）→ 本 PR 的
`test_artifact_freshness.py`（特征目录 + OpenAPI 快照防漂移，+2）→ 合并态 147 条。
答辩统一说「全量 147 条、其中验收套件 90 条」，不再混用历史数字。
可复核：`python -m pytest backend/tests --collect-only -q` → `147 tests collected`；
`grep -rhoE "^\s*def test_" backend/tests --include="*.py" | wc -l` → `122`。
